# Errata and evidence status — 17 October 2026

This note supersedes overstated or incorrect claims in the original FROST review. It distinguishes upstream source inspection, bounded local checks, and historical results reported by the original audit. A source review and a few targeted experiments do not prove the absence of other vulnerabilities. Earlier candidate notes are retained as research history, not as validated findings.

## What was independently checked on 17 October

- In `frost-tools` commit [`53df99c`](https://github.com/ZcashFoundation/frost-tools/commit/53df99c2bd61f7cb60a0d1f634822a76be3799cf), [`frostd::send`](https://github.com/ZcashFoundation/frost-tools/blob/53df99c2bd61f7cb60a0d1f634822a76be3799cf/frostd/src/functions.rs#L190-L237) checks the size of an individual message, then clones that message into a queue for each recipient. No aggregate queue-byte bound appears in this handler. Session creation also accepts a recipient-key list without an evident count cap. This supports the mechanism reported in [issue #611](https://github.com/ZcashFoundation/frost-tools/issues/611).
- A bounded macOS localhost run of that commit used the existing login/session flow. One 65,535-byte message addressed to 64 entries for the same recipient key returned 64 intact queued copies, totaling 4,194,240 bytes of message payload. The run was deliberately too small to test resource exhaustion and did not produce a usable RSS growth measurement. A separate set of 16/128/512-recipient runs accepted the sends but likewise did not independently confirm the reported Linux RSS slope. The bounded run's [result JSON](verification/2026-10-17/queue-copy-results.json) and [Rust driver](verification/2026-10-17/verify_queue_copies.rs) are published for inspection.
- A synthetic local check against `frost-core` 2.2.0/`frost-ed25519` 2.1.0 showed that a constant RNG repeats nonces and that the same nonce with its matching commitment can be passed to `sign()` for two messages. This corroborates the API-level responsibility described below, but is **not** a runtime test of the separately reviewed v3 code. See [result](verification/2026-10-17/nonce-check-results.txt) and [driver](verification/2026-10-17/verify_nonce_safety.rs).

## Historical results whose raw records are not available here

- The [original relay PoC report](reports/frost-application-layer/round2-workerB-pocs.md) records RSS increases at 500/1,000/2,000 recipients and an allocator-failure `SIGABRT` with 29,000 recipients under `ulimit -v 800000` on Linux. The logs and machine image are not included in this repository. The RSS values are **MiB**: the driver divides `/proc` RSS in KiB by 1,024, despite labelling the output “MB.” The reported 31.6/63.1/126.1 MiB series is compatible with roughly 65,535 bytes of queued payload per recipient. `29,000 × 65,535 = 1,900,515,000` bytes (about 1.90 GB/1.77 GiB) is a calculated payload size, **not** measured RSS at the abort.
- The [fuzzing report](reports/frost-application-layer/round2-workerC-fuzzing.md) describes release and debug campaigns with no crash or panic. Its final debug `results.jsonl` has 1,237 **records**, including test events and liveness checks. That does not establish exactly 1,237 HTTP requests; the original draft's “~1,270 requests” is likewise unverified. Raw JSONL files and the XEdDSA helper implementation are not in this repository, so the campaigns cannot be independently audited end to end from these files alone.

## Corrections to the library and application notes

1. **Nonce hedging:** `Nonce::new` hashes random bytes with the secret share. If the random bytes repeat for a given share, the resulting nonce repeats. The earlier statement that a constantly repeating RNG still produces unique nonces was false. The library expects a secure RNG and one-time nonce use; this correction alone does not establish an implementation vulnerability. See [`frost-core/src/round1.rs`](https://github.com/ZcashFoundation/frost/blob/0966bd1/frost-core/src/round1.rs) and [RFC 9591](https://www.rfc-editor.org/rfc/rfc9591.html).
2. **Nonce consumption:** `round2::sign` checks that the supplied nonce commitments match the signing package. It does not track whether that valid nonce/commitment pair was used before. The prior claim that `preprocess()`/`IncorrectCommitment` automatically fail closed on reuse was false. Applications must prevent reuse. See [`round2.rs`](https://github.com/ZcashFoundation/frost/blob/0966bd1/frost-core/src/round2.rs).
3. **Rerandomization:** the v3 `KeyPackage::randomize` method returns a new package; it does not mark the package as consumed with a one-use flag. Documentation instructs callers not to reuse it. `Randomizer::regenerate_from_seed_and_commitments` derives from both seed and encoded commitments, so repeating a seed alone does not guarantee the same randomizer or the linkability asserted in the first report. See [`frost-rerandomized/src/lib.rs`](https://github.com/ZcashFoundation/frost/blob/0966bd1/frost-rerandomized/src/lib.rs).
4. **Cheater detection:** the Round 1 statement that v3 *introduced* default-on cheater detection was inaccurate; the Round 2 review showed it was already a default feature in `frost-core` 2.2.0. The earlier candidate alleging missing culprit identification was withdrawn.
5. **Noise_K candidate:** the original PoC report described an `S` token in the K-pattern handshake. In Noise_K, the static keys are pre-messages; the first message has `E`, `DH(ES)` and `DH(SS)`, not a transmitted `S` token. The proposed peer-impersonation path was withdrawn because it needs the victim's private key. The original mechanistic explanation was wrong.
6. **Signing UI and prior art:** later CLI signing checkpoints display opaque hex, but the earlier Ywallet planning screen can show human-readable amount and recipient data. “Every human checkpoint shows only hex” was too broad. More importantly, the underlying signing-oracle concern was already documented by the maintainers in [frost-tools#333](https://github.com/ZcashFoundation/frost-tools/issues/333) (2024) and by an earlier audit in [frost-tools#475](https://github.com/ZcashFoundation/frost-tools/issues/475) (2025). The present trace is an independent observation of the reviewed snapshot, **not a new finding**. No production wallet exploit or universal absence of deployments was established by the repository searches.
7. **Assurance:** “all leads killed,” “code excellent,” “sound,” and “no critical vulnerability” were broader than the available evidence. The accurate claim is that this review **did not identify** a critical vulnerability in its examined scope; completeness and absence of other flaws are not proven.

## Use in the grant draft

The grant application should cite this note, state that the RSS crash and fuzz campaign are historical reported observations with unavailable raw records, and describe the bounded checks separately. It should not call 1,237 an exact HTTP-request count, imply every result was independently rerun, or infer that publication fulfills the grant program's intended-user acceptance requirement.
